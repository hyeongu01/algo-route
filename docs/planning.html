algo-route 기획서

라면 맵기로 난이도를 매기는 알고리즘 문제 추천 서비스. 이 문서가 기획의 기준이고, 결정이 날 때마다 여기에 반영한다.

개요

프론트는 Next.js(이 레포), 백엔드는 Java Spring Boot(새 레포)로 나눠 만든다.

항목내용
서비스사용자의 실력에 맞는 문제를 추천하고, 풀이 기록을 AI가 평가해 쌓아주는 서비스
난이도서비스 고유 난이도 맵기 1~5 (순한맛 안성탕면 ~ 극강 매운맛 핵불닭볶음면). 관리자가 조정
문제 출처프로그래머스, 리트코드. 문제 본문은 가져오지 않고 링크를 첨부하며, 관리자 또는 크롤러가 메타데이터만 내 DB에 저장
채점직접 채점하지 않는다. 사용자가 외부 사이트에서 푼 뒤 "풀었어요"를 누르면 코드와 메모를 AI가 평가해 기록
추천내 DB의 문제를 기반으로 복습, 약점 보강, 새 개념, 재도전, 적응형, 간격 반복 방식으로 추천
현재 프론트 상태목 데이터(src/data/*)와 브라우저 localStorage 기반. 백엔드가 붙으면 API로 교체

기술 스택

개발자는 NestJS 1년차이고 Prisma, MySQL, Redis에 익숙하다. 이번엔 Spring 생태계 학습이 목적에 포함된다.

영역선택상태
백엔드Java 21, Spring Boot 3.x, Spring Web, Validation, Security확정
ORMJPA(Hibernate), Spring Data JPA, QueryDSL확정
RDBMySQL 8확정
캐시, 세션, 랭킹Redis확정
프론트Next.js 16 (React 19), Cache Components 사용확정
마이그레이션Flyway (SQL 파일 방식, Prisma Migrate에 가장 가까움)제안
API 문서springdoc-openapi, 프론트는 openapi-typescript로 타입 생성제안
빌드, 테스트Gradle(Kotlin DSL), JUnit 5, Testcontainers(MySQL, Redis)제안
패키지 구조도메인별 (user, problem, record, recommend…)제안
로컬 개발 환경Docker Compose (MySQL, Redis)제안

JPA 사용 시 주의

  • Prisma와 달리 연관관계에 접근하면 몰래 쿼리가 나간다. N+1 문제는 fetch join, @EntityGraph로 다룬다.
  • ddl-auto는 개발 초기에만 쓰고, 이후에는 Flyway로 스키마를 고정한다.

아키텍처

프론트와 백엔드는 레포를 분리한다. 브라우저는 Next 한 곳만 호출하고, Next가 /api/**를 Spring으로 넘긴다(rewrites).

flowchart LR
  B["브라우저"] -->|"페이지, /api/**"| N["Next.js 16"]
  N -->|"rewrites /api/**"| S["Spring Boot"]
  N -.->|"서버 컴포넌트 공개 API 호출"| S
  S --> M[("MySQL 8")]
  S --> R[("Redis: 세션, 캐시, 랭킹")]
  S -->|"비동기 평가 요청"| A["Anthropic API"]
  C["관리자, 크롤러"] --> S

같은 오리진 프록시를 쓰는 이유

  • CORS 설정이 필요 없고, 세션 쿠키가 항상 first-party라 SameSite 문제가 생기지 않는다.
  • 서버 컴포넌트에서 인증이 필요한 API를 부를 때는 cookies()로 읽은 세션 쿠키를 Cookie 헤더에 실어 Spring에 전달한다.
  • Next의 proxy.ts(구 middleware)는 UX용 리다이렉트에만 쓴다. 실제 인가는 Spring이 한다.

API 구분

  • 공개 API (/api/public/**): 인증 없이 호출. 서버 컴포넌트에서 쿠키 전달 없이 쓰고 Cache-Control을 신경 쓴다.
  • 인증 API: 세션 필요. 주로 브라우저(CSR)에서 호출.
  • 관리자 API: ROLE_ADMIN 필요.

렌더링 전략

Next 16의 Cache Components에서는 한 페이지 안에 정적 셸, 캐시된 데이터, 요청 시점 스트리밍, 클라이언트 상호작용이 섞인다. 페이지 단위가 아니라 "이 데이터가 누구에게나 같은가"로 나눈다.

페이지방식이유
(home) 홈정적 + 필요한 곳만 use cache누구에게나 같고 SEO 필요. 최근 질문 미리보기만 캐시된 fetch(5~10분)로 교체
problems 목록SSR + 캐시, 필터는 URL 쿼리공개 데이터, 검색 노출
problems/[id] 상세SSR + 캐시(문제 정보), CSR(내 풀이, 메모)공개 부분은 서버, 개인 부분은 클라이언트 컴포넌트
problems/[id]/qnaSSR 목록 + CSR 작성공개 콘텐츠
rankingSSR + 짧은 캐시(약 1분)모두에게 같고 Redis 값을 감싸 보여줌

홈의 HomeHeader, HomeCta는 이미 클라이언트 컴포넌트라 로그인 상태가 정적 셸을 깨지 않는다. 홈에 cookies()를 넣으면 페이지가 동적으로 바뀌므로 넣지 않는다.

인증

세션 방식으로 확정. 웹 전용이고 같은 오리진 프록시 구조라 세션이 가장 단순하고 안전하다.

항목내용상태
방식Spring Session + Redis, HttpOnly 쿠키(SameSite=Lax)확정
1차 소셜 로그인Google (Spring Security OAuth2 Client)확정
2차 소셜 로그인GitHub. user_auth_provider 테이블에 행만 추가하면 되도록 설계확정
이메일/비밀번호 가입프론트에 LoginForm, SignupForm이 이미 있음. 유지하면 password_hash 필요미정
인가Spring Security가 책임. proxy.ts는 UX 가드용확정

AI 평가

LLM 호출은 느리고 실패할 수 있어서 비동기로 처리한다. 사용자는 바로 응답을 받고, 평가 결과는 나중에 채워진다.

sequenceDiagram
  participant U as 사용자
  participant API as Spring Boot
  participant DB as MySQL
  participant W as 평가 작업
  participant AI as Anthropic API
  U->>API: 풀었어요 (코드, 메모, 소요시간)
  API->>DB: solve_attempt 저장, ai_evaluation PENDING
  API-->>U: 즉시 응답 (attemptId)
  W->>AI: 구조화된 출력으로 평가 요청
  AI-->>W: JSON 결과
  W->>DB: ai_evaluation DONE 또는 FAILED
  U->>API: 결과 조회 (폴링)
  API-->>U: 평가 결과

평가 결과 형식

{
  "isCorrect": true,
  "timeComplexity": "O(n)",
  "qualityComment": "해시맵으로 중복을 O(1)에 검사한 점이 좋습니다.",
  "improvements": ["변수명을 의미 있게 바꾸면 읽기 쉬워집니다."]
}

설계 원칙

  • 평가는 PENDING → DONE | FAILED 상태를 가진다. 처음엔 Spring @Async 또는 DB 테이블 기반 작업 큐로 충분하고, Kafka는 쓰지 않는다.
  • 유저별 일일 평가 횟수를 Redis 카운터로 제한한다. 비용 폭주를 막는 장치다.
  • 사용자가 낸 코드와 메모에는 프롬프트 인젝션이 섞일 수 있다. 출력은 JSON 스키마로 강제하고 검증한다.
  • AI가 틀릴 수 있어서 사용자의 status와 AI의 is_correct를 둘 다 저장한다. 맵기와 통계에는 status를 우선 쓰고, is_correct = false면 화면에 경고만 보여주는 안을 제안한다.

개발 단계

1차에서 핵심 루프(가입, 문제, 풀이 기록, 평가, 추천)를 끝낸다.

1차 현재

  • 인증 (세션 + Google)
  • 문제 CRUD, 관리자 수동 등록
  • 풀이 기록, AI 평가
  • 추천 (맵기 계산 포함)
  • 온보딩 초기 맵기

2차

  • Q&A, 게시판 (스포일러 플래그, 채택 답변)
  • 체감 난이도 투표 (spice_vote)
  • 랭킹 (Redis Sorted Set)
  • GitHub 로그인

3차

  • 크롤러 (프로그래머스, 리트코드)
  • 수집 이력 테이블
  • 약관과 robots 정책 확인

맵기와 추천 계산(recommend.ts, initial-spice.ts, analysis.ts)은 서버로 옮기는 것을 권장한다. 그렇게 해야 서버가 신뢰의 원천이 되고 백엔드의 핵심 학습 대상이 된다.
